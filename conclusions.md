# 🎉 Звіт про виконання: Фаза 1 (Data Bootstrapping)

**Статус:** Успішно завершено 🚀
**Стек технологій:** Docker, Apache Airflow (2.9.2), Apache Spark (PySpark 3.5.1), PostgreSQL, Linux.

## 🏗 Що було розроблено та імплементовано

В рамках першої фази ми побудували надійний фундамент для нашого Data-пайплайну. Ми створили скрипт первинного завантаження (`bootstrap.py`), який виконує наступні задачі:

* **Ізольована інфраструктура:** Успішно розгорнуто середовище через Docker Compose (Airflow + PostgreSQL DWH) з налаштованим прокиданням локальних директорій (`dags`, `data`, `logs`).
* **Створення Data Warehouse (DWH):**
* Налаштовано читання "сирих" CSV-файлів (clickstream-дані електронної комерції).
* Реалізовано витягнення унікальних користувачів та генерацію для них випадкових країн (через `F.rand()` та `F.when()`).
* Дані успішно записуються у PostgreSQL (таблиця `dim_users`) через JDBC-драйвер у режимі `overwrite`.


* **Формування Data Lake:**
* Сирі події конвертуються з CSV у високопродуктивний формат **Parquet**.
* Реалізовано партиціювання даних за датою події (`event_date`).


* **Архітектурна ідемпотентність:**
* Пайплайн налаштовано так, щоб його можна було запускати безліч разів без дублювання даних.
* Впроваджено логічне розділення завантажень на рівні тек (`data/lake/raw/events/{місяць}/`), що дозволяє безпечно використовувати режим `overwrite` без ризику видалити дані за інші періоди.

## 📕 Енциклопедія помилок (Troubleshooting Log)

Під час розробки ми зіткнулися з низкою класичних проблем інженерії даних та успішно їх вирішили:

### 1. Битва за права доступу (Docker vs Linux)

> **Симптом:** Контейнер планувальника Airflow (`airflow_ecommerce`) помирав через 30 секунд після старту з помилкою `PermissionError: [Errno 13] Permission denied: '/opt/airflow/logs/scheduler'`.

* **Причина:** Docker створював відсутні папки `logs/` та `data/` від імені `root`, блокуючи доступ звичайному користувачу `airflow` всередині контейнера.
* **Рішення:** Видано повні права через `sudo chmod -R 777 logs data`. Для забезпечення зручності розгортання іншими розробниками (DevEx) у папки додано файли `.gitkeep`, щоб система Git зберігала їхню структуру.

### 2. Відсутність JDBC Драйвера

> **Симптом:** `java.lang.ClassNotFoundException: org.postgresql.Driver` під час спроби запису в базу.

* **Причина:** PySpark працює на базі JVM і не містить вбудованих драйверів для роботи з PostgreSQL "з коробки".
* **Рішення:** До конфігурації `SparkSession` додано автоматичне завантаження потрібного пакета: `.config("spark.jars.packages", "org.postgresql:postgresql:42.6.0")`.

### 3. Конфлікт перезапису файлів у Data Lake

> **Симптом:** `Unable to clear output directory... Failed to delete file or dir: it still exists.`

* **Причина:** Спарк у режимі `overwrite` намагався видалити директорію перед записом, але отримував відмову від Linux через конфлікт власників папок (Docker проти хост-системи).
* **Рішення:** Застосовано рекурсивне оновлення прав (`sudo chmod -R 777 data`). Надалі проблему повністю вирішено архітектурно — шляхом ізоляції кожного набору даних у власну підпапку.

### 4. Голод оперативної пам'яті (OOM - Out of Memory)

> **Симптом:** `java.lang.OutOfMemoryError: Java heap space` та попередження `Total allocation exceeds 95.00%`.

* **Причина:** За замовчуванням Spark виділяє лише 1 ГБ пам'яті. Для обробки масивних CSV-файлів (по 5-8 ГБ) цього виявилося критично мало.
* **Рішення:** Збільшено ліміт пам'яті драйвера до 8 ГБ через конфігурацію `.config("spark.driver.memory", "8g")`.

### 5. Фантомні файли та Рекурсія-вбивця (Py4J Bug)

> **Симптом:** Скрипт падав миттєво з незрозумілою помилкою `RecursionError('maximum recursion depth exceeded')`.

* **Причина:** Баг сумісності обробника помилок Python 3.11 та PySpark. При введенні назви файлу в термінал потрапляли невидимі спецсимволи (наприклад, від натискання `Backspace` або перемикання мови). Spark не міг знайти такий "зламаний" шлях і генерував помилку `PATH_NOT_FOUND`, яку Python не міг коректно вивести на екран, зациклюючись у рекурсію.
* **Рішення:**
1. Додано `.strip()` для очищення вводу користувача від невидимих символів та пробілів.
2. Вимкнено `inferSchema=True` під час читання CSV для застосування лінивих обчислень (Lazy Evaluation) та значного прискорення старту.
3. Додано блок `try...except Exception as e`, щоб перехоплювати та читати справжні помилки до того, як спрацює баг рекурсії.



### 6. Проблема "Двох Господарів" при видаленні папок

> **Симптом:** Неможливість видалити тестову папку `events` командою `rm -rf` через термінал Linux.

* **Причина:** Нові папки (партиції Parquet) створювалися процесом Docker, тому Linux призначав власником файлів саме його, блокуючи доступ звичайному користувачу хост-системи.
* **Рішення:** Видалення таких згенерованих папок виконується виключно з правами суперкористувача (`sudo rm -rf`).
